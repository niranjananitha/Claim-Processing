# Claims Management Frontend Integration & Redesign Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. The redesign task additionally invokes the frontend-design skill.

**Goal:** Connect the existing Next.js claims UI to the real FastAPI backend (replacing all mock/localStorage state), implement real role-based auth, remove the notification system (keep the bell icon), and raise the visual design to a professional enterprise standard.

**Architecture:** Keep the Next.js 16 App Router and the existing pages/components. Introduce one real API client (`app/services/api.ts`) that holds the access token in memory, sends `credentials: "include"`, and transparently refreshes on 401. `ClaimsContext` becomes API-backed (no localStorage claims, no mock). Field shapes are mapped snake_case↔camelCase at the API boundary so the existing `ClaimRecord`-based components change as little as possible.

**Tech Stack:** Next.js 16.4.3, React 19, TypeScript, Tailwind v4. Verification via `npx tsc --noEmit` + `next build`, and behavioral checks with the Playwright MCP tools against the running stack.

**Spec:** `docs/superpowers/specs/2026-11-03-claims-management-system-design.md`. Backend plan (contracts this targets): `docs/superpowers/plans/2026-11-03-backend.md`.

## Global Constraints

- Do NOT change the framework or introduce a new design system. Improve the existing Tailwind UI; reuse good existing elements.
- This is a newer Next.js than training data: before writing routing/server code, read the relevant guide under `frontend/node_modules/next/dist/docs/` (per `frontend/AGENTS.md`).
- API base URL: `http://localhost:8000/api/v1` via `NEXT_PUBLIC_API_BASE_URL`. **Use `localhost`, never `127.0.0.1`** — same-site with `localhost:3000` so the `SameSite=Strict` refresh cookie is sent. Frontend runs on `localhost:3000`.
- Every API call uses `credentials: "include"`. The access token lives in a JS module variable (memory) only — **never** in `localStorage`/`sessionStorage`. The refresh token is the backend's httpOnly cookie and is never read by JS.
- Canonical claim statuses (exact strings) match the backend: `Submitted`, `Under Review`, `Action Required`, `Agent-Verified`, `Fraud Review`, `Approved`, `Rejected`, `Disputed`, `Revaluation`.
- Public registration creates **clients only** (no role selector on signup). Agent/manager accounts come from the backend seed/manager endpoint.
- **No notification feature**: delete the notifications page, the sidebar "Notifications" nav item, `notificationsApi`, the fake header dropdown contents, and notification mock data. Keep the header bell **icon** as a static, non-interactive element (no count badge, no dropdown, no API).
- Authorization is enforced by the backend; frontend route guards are UX only.
- Mock data (`app/lib/mockData.ts`) must not feed production workflows; keep it only if a non-production dev/test path needs it.

## Review Focus

- **Session survives page refresh:** on reload the in-memory access token is gone; the app must silently call `/auth/refresh` (cookie) and restore the session, or cleanly show logged-out. (Exercised in Task 3 + Task 11.)
- **Expired access token mid-use:** a 401 on any call triggers one refresh-and-retry; a failed refresh routes to login without a crash loop. (Task 1 + Task 11.)
- **Role lands on the right portal:** client→`/`, agent→`/agent`, manager→`/manager`; a user typing another role's URL is redirected. (Task 3.)
- **Backend-down / error states:** every data page shows a loading state, an empty state, and a readable error state instead of a blank screen or a thrown error. (Tasks 6–9, polished in Task 10.)
- **ML OFFLINE / imputed features:** the ML panel renders real results, shows which features were imputed, and shows a clean "model offline" state when `model_status==="OFFLINE"`. (Task 9.)

### Task 1: Real API client (`app/services/api.ts`) + types

**Files:**
- Rewrite: `frontend/app/services/api.ts`
- Create: `frontend/app/services/types.ts` (shared TS types), `frontend/.env.local` (`NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api/v1`)

**Interfaces (Produces):**
- `setAccessToken(t: string | null)`, in-memory token store.
- `api.request<T>(path, options)` — adds `Authorization` when a token exists, `credentials:"include"`, JSON by default (skips for FormData); on 401 (except auth routes) calls `/auth/refresh` once, stores the new token, retries; returns `{ok, status, data?, error?}`.
- Domain clients matching the backend contract exactly: `authApi.register/login/refresh/logout/me`, `claimsApi.list/get/create/changeStatus/history`, `policiesApi.list/get`, `agentApi.dashboard/assignedClaims/verify/requestInformation`, `managerApi.dashboard/pendingClaims/approve/reject/revaluation`, `dashboardApi.summary`, `documentsApi.upload/downloadUrl/delete`, `mlApi.predict/getPrediction`.
- `toClaimRecord(apiClaim)` / `toClaimCreate(form)` — snake↔camel mappers so existing components keep using `ClaimRecord`.
- **No `notificationsApi`.**
